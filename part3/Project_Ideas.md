# Part 3 專案構想建議 (Project Ideas)

既然是「物件導向程式設計 (OOP)」的期末專案，**重點不在於你的 AI 有多強，而在於你的程式碼架構設計得有多漂亮、多符合 OOP 原則**。

以下提供三個具體且可行的專案構想，難度由淺入深，你可以根據組員的興趣選擇：

## 構想一：打造「通用強化學習實驗室」 (基於經典環境)
**難度：⭐⭐ (適合想專注於架構設計，不想花時間寫遊戲邏輯的組別)**

這個方向是選擇 Gymnasium 內建的環境（如 `CartPole-v1` 或 `MountainCar-v0`），但重點在於**設計一套通用的訓練架構**。

*   **要做什麼？**
    *   不要把訓練程式碼寫成一坨 `while` 迴圈。
    *   設計一個抽象基底類別 (Abstract Base Class) 叫做 `Agent`。
    *   實作繼承自 `Agent` 的子類別，例如 `RandomAgent` (隨機亂動)、`QTableAgent` (使用 Q-Table)、`HumanAgent` (讓人類用鍵盤玩)。
    *   設計一個 `Trainer` 類別，負責管理環境與 Agent 之間的互動迴圈。

*   **OOP 亮點在哪裡？**
    *   **抽象 (Abstraction)**：`Agent` 基底類別定義了 `act(observation)` 和 `learn(reward)` 等抽象方法，隱藏了演算法細節。
    *   **多型 (Polymorphism)**：`Trainer` 不需要知道現在是哪個 Agent 在跑，它只管呼叫 `agent.act()`，不同的 Agent 會表現出不同的行為。
    *   **封裝 (Encapsulation)**：將 Q-Table 的更新公式封裝在 `QTableAgent` 內部，外部無法直接修改 Q-Table。

## 構想二：進階版「地牢探險」 (基於自定義環境)
**難度：⭐⭐⭐ (適合覺得範例太無聊，想做點遊戲開發的組別)**

這個方向是直接拿 `part3` 提供的 `warehouse_robot.py` 來魔改。原本只是機器人找箱子，你可以把它變成一個 RPG 地牢遊戲。

*   **要做什麼？**
    *   **擴充地圖元素**：除了地板、機器人、目標，新增「牆壁 (Wall)」、「陷阱 (Trap, 扣分)」、「鑰匙 (Key)」、「門 (Door, 有鑰匙才能過)」。
    *   **引入敵對生物**：新增會在地圖上巡邏的「怪物 (Monster)」。

*   **OOP 亮點在哪裡？**
    *   **繼承 (Inheritance)**：
        *   建立一個 `GameObject` 父類別。
        *   `Player`, `Enemy`, `Item` 都繼承自 `GameObject`。
        *   `Item` 下面還可以分 `Key`, `Potion`, `Treasure`。
    *   **多型 (Polymorphism)**：
        *   每個物件都有 `on_collision(target)` 方法。
        *   撞到 `Wall` -> 擋住。
        *   撞到 `Trap` -> 扣血。
        *   撞到 `Key` -> 撿起。
    *   **組合 (Composition)**：`Player` 類別裡面可以包含一個 `Inventory` (背包) 物件。

## 構想三：智慧交通號誌模擬 (自定義環境 + 模擬)
**難度：⭐⭐⭐⭐ (適合想挑戰模擬真實世界問題的組別)**

設計一個十字路口，車子會隨機出現，Agent 的任務是控制紅綠燈，讓車流最順暢（等待時間最短）。

*   **要做什麼？**
    *   設計 `Car` 類別：有速度、位置、等待時間。
    *   設計 `TrafficLight` 類別：有狀態 (紅/綠/黃) 和計時器。
    *   設計 `IntersectionEnv`：管理車子生成和移動。

*   **OOP 亮點在哪裡？**
    *   **物件導向建模**：將真實世界的實體（車、燈、路）轉化為程式碼中的類別。
    *   **狀態管理**：每個 `Car` 自己管理自己的狀態，環境只負責協調。

---

## 建議
如果你們時間有限，**強烈建議選擇「構想二：進階版地牢探險」**。
1.  **起步快**：你們已經有 `warehouse_robot.py` 的程式碼了，不用從零開始。
2.  **效果好**：加幾個圖片 (Sprite) 和規則，展示起來視覺效果很強，很容易說明你們做了什麼擴充。
3.  **OOP 結構明確**：遊戲物件的繼承關係 (Entity -> Player/Enemy) 是教科書等級的 OOP 範例。
